## FLAG
- [antipatterns] t-11's darwin 'x64 slice' launch cannot work as written. `_electron.launch({executablePath: '/usr/bin/arch', args: ['-x86_64', exe]})` puts Playwright's own arguments first. playwright-core 1.64.1 (`lib/coreBundle.js` ~L45668) builds `["--inspect=0", "--remote-debugging-port=0", ...options.args]`, so the spawned command is `/usr/bin/arch --inspect=0 --remote-debugging-port=0 -x86_64 <exe>`. `arch` rejects `--inspect=0` as an unknown architecture before the app starts. smoke.packaged 'x64 slice' (c-2) will be red. Nobody will see that until t-14's PR run, because t-11 is not observable on the dev Mac when real userData exists.
  Suggestion: give t-11 a launch mechanism whose argument order is under its control. Two options: an executable wrapper script, passed as executablePath, that runs `exec /usr/bin/arch -x86_64 "<exe>" "$@"`; or a plain child_process spawn of `arch -x86_64 <exe>` with the port found by a probe, as t-12 does on Windows. Also confirm that Rosetta 2 is present on the macos-15 arm64 runner image.
- [antipatterns] t-13's publish job is unlikely to be able to download its own artefacts. It is limited to `contents: write` with no `uses:` and fetches artefacts with `gh run download "$GITHUB_RUN_ID"`. That call goes to the Actions artifacts API, and the GITHUB_TOKEN normally needs `actions: read` for it. Once a job lists any permission, every unlisted scope becomes `none`. The plan forbids adding that scope twice: t-13's contract says "publish has more than contents: write → release-workflow.spec fails", and the existing workflow-policy.ts accepts only `{}`, `contents: read` or `contents: none` at job level. If the token is refused, nothing publishes. That outcome is safe, but it first shows up on the real v0.1.5-rc.1 tag, after merge, because no PR check runs publish against the real API. The stub-gh test cannot catch it.
  Suggestion: before t-13 runs, I (the reviewer) suggest that the plan author settle how publish gets the artefacts: check GitHub's docs or run a throwaway workflow. If `actions: read` is required, amend t-13's contract and the workflow-policy rule to allow exactly `actions: read` on publish. The locked decision only reserves `contents: write`, so a read scope does not conflict with it.
- [antipatterns] t-13's tag job says "checkout fetch-depth 0, no install, runs release-tag.ts", but does not require setup-node. release-tag.ts relies on Node type stripping. The repo pins Node 24.14.0 in `.node-version`, but the ubuntu-24.04 image's default `node` may be older and may not strip types. No t-13 contract line checks Node setup for the tag job, so a missing setup-node only fails on a real tag.
  Suggestion: add a t-13 contract line requiring that the tag job uses SHA-pinned setup-node with `node-version-file: .node-version` and no `cache:`.
- [test-contract] No test checks the tray 'Restart to update' wiring end to end. The t-10 description says "onReady calls tray.setUpdateReady(true)" and that the updater is built "with the existing notifier", but none of t-10's ten contract lines checks either connection. t-12 calls `handle.restart()` directly, which skips the tray, and checks `status().notified`, which is the updater's own bookkeeping and not proof that the notifier was called. If main.ts drops both connections, every listed test still passes, yet c-5 says CI proves the notification and the tray item on Windows and Linux.
  Suggestion: add a t-10 boundary.spec source-order check that onReady reaches `setUpdateReady(true)` and that createUpdater gets the real notifier. Or have t-12 read the tray menu labels through the published handle after 'downloaded'.
- [antipatterns] Before t-14 runs, t-11 and t-12 are committed with no evidence about their own contracts. Every contract line in both is a Playwright packaged e2e, so the per-task vitest+lint gate is green without testing them. The plan says so openly. However, t-14's `files` are only ci.yml and ci-packaged.spec.ts. If its PR run shows a defect in t-5, t-10, t-11 or t-12 (the arch issue above is one), the plan has no task that can carry the fix.
  Suggestion: say in t-14's description where fixes go when the PR run is red (reopen the failing task, or /dross-quick), so a fix does not land in t-14's commit outside its declared files.
- [antipatterns] t-14 bakes the loopback feed into Windows and Linux A only. The macOS PR build and all three release builds therefore launch with the GitHub provider and contact live github.com during the packaged smoke. t-11's 'offline update check' contract only covers the case where the loopback feed is unreachable. The macOS smoke therefore depends on github.com being up, and on an unsigned app it would try a real Squirrel.Mac download if a newer release than the branch version ever exists.
  Suggestion: either bake the loopback feed into macOS A too (t-2 already allows it for unsigned builds), or extend t-11's contract to say that a GitHub-provider check failing or finding nothing leaves the window up.
- [granularity] t-2 combines three concerns: the pure electron-builder config (decision artefacts), the packaging CLI with its file checks, and the signing-credential gate (decision release_secrets, c-4 "missing Apple credential"). It has 19 contract lines, the largest single commit in the plan. Its 4 files are under the threshold, but a red line in the signing gate holds back the config that t-9 and everything later depends on.
  Suggestion: consider splitting the `--sign` credential gate and the no-values-printed checks into their own task.
- [granularity] t-1 and t-10 each touch 5 files, which meets the split threshold. Both are cohesive: t-1's lockfile, workspace and package.json form one unit, and t-10 is a single wiring change. Recorded for the mechanical rule only.
  Suggestion: no split needed. Keep them as they are unless they grow.
- [wave-order] t-13 depends on t-11, but t-13 only needs the text `test:e2e:packaged` in release.yml. release-workflow.spec and ci:policy check workflow text, not whether package.json scripts exist. Its real inputs are t-3 (release-tag.ts, release.json), t-7 (the reader) and t-9 (expectedArtefacts, verify-packaged). Dropping the t-11 edge would let t-13 run in wave 4, alongside t-11.
  Suggestion: drop the t-11 dependency, or keep it and state that the reason is coherence (never commit a workflow that names a missing script).

## Summary

Before t-13 runs, someone also needs to confirm that the publish job can fetch artefacts with only `contents: write`, and that the tag job gets a Node version that can strip types. Every one of these failures would surface only in t-14's PR run or on the first real tag.
