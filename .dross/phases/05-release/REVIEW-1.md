# Plan Review — 05-release

Reviewed: 2026-11-14
Plan: 14 tasks across 6 waves

## BLOCKING
- [antipatterns / files] t-12 cannot meet its contract "if the updater state lists B as notified other than exactly once after a second forced check" within its declared files. Both halves of that check need something the updater handle does not expose. t-4 defines the handle as `publishUpdaterHandle({status, restart})`, and `status()` only carries 'idle' / 'checking' / 'downloaded' plus a version. t-10 publishes exactly `{status, restart: restartToUpdate}`. So there is no way to force a check and no record of which versions were notified. t-12's files (update.packaged.ts, launch-packaged.ts) cannot add either. The main bundle is ESM ("type": "module"), so an `electronApp.evaluate` cannot `require('electron-updater')` to reach the singleton. Worse, t-12 cannot run on the macOS host, so this only shows up in t-14's PR run, two waves after the tasks that would need changing.
  Suggestion: either extend t-4's handle contract (for example a `check()` and the notified-version list in `status()`) and t-10's `publishUpdaterHandle` arguments to match, or drop that clause from t-12. t-4's updater.spec already pins "one notifier show per version" at unit level.

## FLAG
- [test contract] t-13's release-workflow.spec never asserts that each build job has `needs: tag`. It only pins `publish.needs`. The `release` environment admits any `v*` tag no matter which commit it points at (t-3 policy), so the tag job is the only thing standing between an off-main tag and the macOS job reading CSC_LINK and notarising. Without that `needs`, the job would sign and notarise off-main code before the publish job refuses. The locked `release_pipeline` decision ("a cheap first job checks the tag") implies this gating, but no contract enforces it.
  Suggestion: add a release-workflow.spec clause that build-macos, build-windows and build-linux each list `tag` in `needs` and take `--version` from `needs.tag.outputs.version`.
- [test contract] t-2's asarUnpack contract names only `drizzle/0000_little_dreaming_celestial.sql`. t-10 points the server cwd (and so `migrationsFolder()` = `<cwd>/drizzle`, src/lib/server/db/migrate.ts) at `app.asar.unpacked`. Drizzle's migrator reads `meta/_journal.json` and all 12 `.sql` files from that folder. A `drizzle/*.sql` pattern passes t-2 but breaks packaged startup, and the first place that shows is t-11's smoke, which may itself first run in t-14's CI.
  Suggestion: make the t-2 contract also require `drizzle/meta/_journal.json` and the newest migration (`drizzle/0011_drop_auth.sql`) to match asarUnpack.
- [test contract] t-1 widens `supportedArchitectures.cpu` to `[current, x64, arm64]` on every host. On the Linux runner that also installs `@libsql/linux-arm64-gnu`. t-9's verifyLayout rejects "linux ships linux-arm64-gnu", but no t-2 contract says the per-OS `files` / unpack patterns exclude foreign-arch `@libsql/*` packages. Unless electron-builder's pnpm collector already filters optional deps by os/cpu (the plan does not say it does), the AppImage fails `verify-packaged layout` for the first time in t-14's PR run.
  Suggestion: either add a t-2 clause that the linux config excludes `@libsql/linux-arm64-*` and musl builds and the win config excludes everything except `win32-x64-msvc`, or record in t-2 that electron-builder's filtering was checked and is relied on.
- [antipatterns / files] t-12's Windows contract ("GET / on its listening port lacks the seeded watch title") needs the relaunched process's port. t-8's process-probe builds a pid→port map only from Linux `ss -Hltnp`. On Windows it parses Get-Process / Get-CimInstance, which give {pid, path, startTime} but no ports. t-12 would have to put netstat or Get-NetTCPConnection parsing inline in update.packaged.ts, where no vitest spec covers it.
  Suggestion: add a Windows listener parser (Get-NetTCPConnection JSON or `netstat -ano`) to t-8's contract, alongside the `ss` one.
- [antipatterns] t-11's darwin "spawns the app under `arch -x86_64` and GETs the watchlist" does not say how the x64 launch learns its port. t-8 has no macOS (lsof) parser, and t-11 does not depend on t-8 anyway. If the intent is `_electron.launch({executablePath: '/usr/bin/arch', args: ['-x86_64', exe]})` and reading the first window URL, the description should say so.
  Suggestion: name the mechanism in t-11's description so the writer does not invent untested port scraping.
- [locked-decision wording] t-13 allows the publish job a `uses:` of download-artifact. The locked `release_pipeline` decision says the publish job "runs no repo or dependency code, only gh". A first-party, SHA-pinned action is not npm dependency code, so the decision's security intent holds. Even so, the plan departs from the decision's literal text without saying so. `gh run download "$GITHUB_RUN_ID"` would match it exactly.
  Suggestion: either switch the contract to `gh run download`, or note in t-13 that download-artifact is accepted under the decision's intent.
- [global instructions] t-13 scaffolds a new pipeline, and t-14 adds universal packaging to every PR on all three OSes, plus a second packaging (build B) on Windows and Linux. The global CLAUDE.md requires reading `~/.claude/memory/reference_ci_pipeline_optimisation.md` when scaffolding a pipeline or adding runner load. Both tasks cite only the supply-chain reference. t-14's "timeout goes up" also gives no value: the test job's current limit is 45 min.
  Suggestion: have the t-13 and t-14 executors read the optimisation reference too, and state t-14's new `timeout-minutes`.
- [granularity] t-10 touches 5 files and carries two separable concerns. One is the packaged-cwd fix (`serverCwdFor`, c-1). The other is updater and predecessor-pid wiring (c-5/c-6) plus the boundary and harness.e2e changes. It is a split candidate. Keeping it whole is defensible, because both halves edit main.ts and splitting would mean two consecutive main.ts edits.
  Suggestion: the author's call. If kept, no change is needed.

## NOTE
- [observation] Whether t-11 and t-12 work is first observed in t-14's PR CI: t-12 always, and t-11 whenever `~/Library/Application Support/price-check` already exists locally, which any earlier `pnpm dev:desktop` run creates. release.yml (t-13) is not executed at all until the v0.1.5-rc.1 tag. This follows from the coordinator's constraints (no secrets, packaging needs real runners), and the plan states it honestly in the task logs. Expect any fixes to land as commits after t-14, and treat rc.1 as release.yml's dry run.
- [observation] The macOS PR smoke and every release-job smoke run packaged builds with the GitHub provider. So the launch-time update check makes a live, unauthenticated call to GitHub Releases from shared runner IPs. t-11's 'offline update check' contract covers only the loopback case. r-01 is not violated (it covers shop sites), but once a newer release exists, the macOS PR smoke would background-download it during the test.
- [observation] t-6 removes the "Not released yet" note in the phase. Between the merge to main and a successful v0.1.5 tag, which takes longer if rc.1 fails, the README describes downloads that do not exist yet.
- [observation] The v0.1.5 tag passes t-3's version check only if the execute-start bump has set package.json to 0.1.5, and no task checks that. t-2's local observation uses `--version 0.1.4`, which is harmless because any valid version works there.
- [coverage] All six criteria are covered. t-6 → c-1 and t-7 → c-1/c-4 are thin claims, since those tasks are documentation and plumbing. The real coverage of those criteria sits in t-2, t-9, t-11, t-13 and t-14.
- [granularity] t-1 trips the 5-file threshold, but its pnpm-lock.yaml and pnpm-workspace.yaml changes are mechanical. Splitting off the gitleaks line would only add a commit ahead of the wave-1 gate.
- [strength] Secrets handling meets the coordinator's constraint end to end. No task needs a real credential. t-2 refuses `--sign` before `build()`, names only the missing variables, and has a sentinel-value contract against printing them. t-3 records the environment as a spec-checked JSON file with a tag-type `v*` policy and an explicit no-secrets assertion. t-13 confines `secrets.` to one step's env and keeps it out of every `run:` body.
- [strength] The test contracts name concrete failure mechanisms rather than "tests pass". Examples: GitHub renaming 'Price Check' assets so that latest*.yml 404s; `detectUpdateChannel` producing rc.yml; an x64ArchFiles glob too broad to catch a missing lipo; a branch-type `v*` policy leaking secrets to a branch named v1; drafts counted in the existing-release check.
- [strength] The c-6 design holds together. Install starts only after the DB is closed, enforced by a call-order log. ALERTS_ENCRYPTION_KEY and DATABASE_URL are scrubbed before the installer inherits the environment. A predecessor-pid wait covers the AppImage relaunch race. The packaged smoke refuses to run over an existing real userData dir.

## Summary
The plan is thorough, consistent with all locked decisions, and covers every criterion. It should not proceed until t-12's forced-check and notified-list contract has an updater-handle surface to run against. The flags are cheap contract additions that move failures from t-14's CI run back into vitest.
