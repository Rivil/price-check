## BLOCKING
- [wave-order] t-7 cannot go green at its own commit. Its removed-routes.spec contract fails if "any non-test file under src/ matches /better-auth|locals\.user|\/api\/auth/". `src/env.ts:24` (the BETTER_AUTH_SECRET description) contains `https://www.better-auth.com/docs/installation`, which matches `/better-auth/`. env.ts is not in t-7's files. Only t-8 edits it, and t-8 runs in wave 5, after t-7. The t-7 executor will then have to edit env.ts outside its scope, weaken the scan, or commit red.
  Suggestion: move the BETTER_AUTH_SECRET entry removal from env.ts into t-7, or move the src-wide `better-auth` scan assertion from t-7 to t-8. Re-check the scan regex against every non-test src file that t-7 does not delete. `src/routes/+page.server.ts:15` has a `locals.user` comment that t-5 must remove.

## FLAG
- [test-contract] t-12's 4th contract requires "a missing Host" to answer 403. The repo runs Node 24.14.0 (`.node-version`). Since Node 20, `http.createServer` defaults to `requireHostHeader: true`, so it answers any HTTP/1.1 request without a Host header with 400 before adapter-node or hooks run. The Host guard can never produce that 403, so the assertion fails no matter how correct the guard is. Also, node:http's client adds a Host header unless `setHost: false` is passed.
  Suggestion: let the missing-Host row accept 400 or 403 (anything but 2xx), or send it as HTTP/1.0 if the guard's own 403 is what has to be proven. Either way, the task should say which one it means.
- [wave-order] `pnpm check` goes red at t-9 and stays red until wave 7. t-9 removes `signIn`, `submitLogin` and the `SEEDED_<user>` credentials from `e2e/accounts.ts`. But `tsconfig.json` includes `src`, so svelte-check type-checks `src/routes/{at-target,contrast,focus,watchlist,header,chart-a11y,layout}.e2e.ts`, `watches/[id]/watch-page.e2e.ts` and `account/alerts/alerts.e2e.ts`. All of these still import `signIn` until t-10 and t-11 rewrite them. CI runs `pnpm check` (ci.yml:52). The vitest gate won't catch this, but the t-9 commit is not type-clean.
  Suggestion: either have t-9 keep the removed exports as temporary shims until t-10/t-11, or state explicitly that intermediate commits may fail typecheck. The PR only needs to be green at the end, since CI triggers on pull_request only.
- [wave-order] The e2e suite can't run at all from t-4 through t-9. The Playwright webServer command starts with `node e2e/seed.ts`. seed.ts imports `alertChannel` from schema.ts, and t-4 drops that table and export. seed.ts also imports `createAuth` from `auth-factory.ts`, which t-7 deletes. `e2e/harness.e2e.ts` also calls `loadChannelConfig`, whose signature t-4 changes. So header, layout and footer changes from t-3 and route changes from t-4 to t-8 get no e2e signal until wave 7, and a regression there will show up mixed in with the e2e rewrite noise.
  Suggestion: accept this knowingly, or after t-9 lands, run the old page-flow e2e once before t-10 and t-11 rewrite them so regressions can be told apart from rewrite churn.
- [test-contract] t-6's 3rd contract says "if hooks.server.ts still imports better-auth or #lib/server/auth.ts, hooks.server.spec fails at module load (the spec has no better-auth mock)". That relies on side effects. better-auth is still installed at t-6 (t-8 removes it), so importing `better-auth/svelte-kit` loads fine without a mock. Whether real `auth.ts` throws depends on what the `$app/env/private` mock exports. If the spec just drops its `vi.mock('#lib/server/auth.ts')`, a leftover import could pass silently. t-7's source scan catches it later, but not at t-6's commit.
  Suggestion: make the contract a direct assertion, e.g. read hooks.server.ts `?raw` and expect no `better-auth` or `#lib/server/auth` import.
- [granularity] t-4 touches 25 files across 4 layers (schema + migration, alerts libs, hooks, route + Svelte page), and t-5 touches 21 files across 3 layers. The description justifies this (schema, libs and callers must change in one commit to stay green). But for a cold per-task writer and reviewer, these are the highest-risk tasks in the plan. The `+page.svelte` / `page.svelte.spec.ts` part of t-4 (dropping `loginEmail` from the email cards) is UI-only and doesn't need to share the migration commit.
  Suggestion: think about moving t-4's Svelte-component half into its own follow-up task. If not, budget explicit pair checkpoints inside t-4 and t-5.

## NOTE
- [coverage] Every criterion (c-1 to c-7) is covered by at least one task. c-6 is covered only by t-12. t-1's `covers = ["c-5"]` is a stretch, since a test harness doesn't deliver persistence. c-5 is really proven by t-5 ('restart keeps data', 'idempotent restart') and t-13 (restart.e2e).
- [locked-decisions] No conflicts. data_scope: t-4, t-5 and t-7 remove every user_id column, index and auth table, and t-7's 'install-owned schema' contract asserts this. removed_routes: t-12 asserts exact 404 with no Location header. local_request_guard: t-2, t-6 and t-12 cover /health, and t-12 asserts no `csrf.trustedOrigins` override. The static `/_app/immutable/*` gap goes against the letter of "every request", but the spec defers it to 03-desktop-shell, so the plan just follows the spec.
- [accuracy] t-6 says "admin routes still import [access.ts] until then". They don't. The admin `+page.server.ts` files import `auth.ts` and `accounts.ts`. access.ts is imported only by hooks.server.ts (t-6), +layout.server.ts (t-3), access.spec.ts and accounts.spec.ts. This is harmless, but it is the stated reason access.ts is deleted in t-7 rather than earlier.
- [accuracy] t-7 calls itself "Pure deletion", but it also writes destructive migration 0011, a new removed-routes.spec and new migrate.spec cases. The contracts cover the risky parts ('upgrade 0010->0011', 'schema matches snapshot'), but the label understates the review effort.
- [behaviour] t-4 changes `channelAad` from user-scoped to `['alert-channel', kind]`. After 0009, every encrypted channel carried over from a 0008 DB stays in the table but becomes undecryptable, and channelsFor skips it. This is consistent with the milestone non-goal (no import of old server data, no installs yet), but it means the "1 encrypted channel keeps its id" upgrade row keeps a channel nobody can open.
- [rules] No violations. runtime.mode is native, so pnpm is correct. r-01 is respected and named explicitly (stubbed checks, `.invalid` ntfy host, rows inserted via createDb instead of UI adds). No private infra (r-03) appears; all foreign hosts are `evil.example` or `.invalid`.
- [strength] The migration contracts target the real SQLite hazards rather than "migration runs". They cover cascade-on-rebuild (DROP TABLE firing ON DELETE CASCADE), skipped migrations (journal `when`), a multi-user DB being rejected *and* left at 0008/0009, and a snapshot-vs-PRAGMA drift check backed by `db:generate` emitting nothing.
- [strength] The Host guard is specified adversarially. It reads the Host header and never `event.url` (built from ORIGIN). Its reject table covers look-alike hosts that defeat `startsWith`/`includes`. The ignored X-Forwarded-Host case and the "spawned WITHOUT ORIGIN" case isolate the Host guard from Kit's CSRF check, since in that case only the guard can return 403.
- [strength] The deletion sequencing is sound. Importers of each auth module move off it before the module is deleted: auth-harness via t-1 then t-4/t-5 then t-7, access.ts via t-3/t-6 then t-7, and the better-auth package in t-8 only after t-7. node-server.ts uses an env allowlist (no `process.env` spread), so "starts without BETTER_AUTH_SECRET" can't pass just because the variable leaked in from the parent environment.

## Summary
The plan is strong and its contracts are unusually specific, but t-7's own src-wide `better-auth` scan fails on `src/env.ts`, which isn't cleaned until t-8. Fix that ordering before executing, and fix the t-12 missing-Host expectation, which Node 24's HTTP server makes unachievable.
